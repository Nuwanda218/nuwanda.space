# Nuwanda Space 前端设计、开发与优化流程草案

日期：2026-10-23。范围：现有 Astro 博客的本地设计与后续迭代。

本轮用户已选择：第一轮先做“首页与整体视觉”，确定网站气质。下文的风格、布局和功能顺序是建议，尚未作为最终视觉方案实施。

## 1. 当前定位与证据边界

当前最需要解决的是内容组织与视觉表达：素材如何进入页面、不同内容如何阅读、首页如何引导访客。它位于“素材与内容模型 → 展示组件 → 页面与导航”链路中，影响首页、内页和移动端。优先级高于增加动效和工具依赖。

本轮阅读了当前源码、素材与项目说明：

- 技术基础：`package.json` 锁定 Astro 7.3.8，使用原生 Astro 组件、CSS 与 Node Adapter；当前配置保留静态页面和按请求运行的 SSR/API。
- 内容入口：`materials/site/profile.json` 管理个人文案；`materials/life`、`materials/notes`、`materials/guard` 管理三个栏目。继续维持“放入文件即可接入”的写作方式。
- 现有首页：`src/pages/index.astro` 组合摄影封面与页脚；`presentation.ts` 当前选用树下自行车照片。首页已有三个栏目入口。
- 现有气质：米白底色、深灰绿正文、绿色强调、专题红色，搭配衬线标题和无衬线正文。
- 已有真实记录：“晚训与树下的自行车”。三篇笔记、两条专题事件及朋友合照记录目前标记为演示。演示数量不能作为已发表内容数量宣传。
- 阅读缺口：笔记目前在列表中通过原生 details 展开，没有独立文章详情路由。
- 当前 Git 工作区已有大量历史修改、删除与未跟踪文件。后续动手前建立定向基线，不能把这些状态当作新任务造成的变更。
- 项目根目录 `.workbuddy-ai/memory/MEMORY.md` 当前不存在；历史信息仅用于定位，本轮结论以当前文件为依据。旧路线文档中仍有早期静态站、Cloudflare 与无服务器 Node 等历史设想，不能直接作为现行开发要求。

本轮未修改站点代码、运行构建、检查当前浏览器画面或核验线上状态。以下验收要求是后续标准，不是本轮已通过的结果。

## 2. 内容与体验定位

建议定位：以个人摄影建立记忆点，以文章承载思考，以专题保存共同经历的个人空间。

| 区域 | 访客目的 | 建议呈现方式 |
| --- | --- | --- |
| 首页 | 认识作者、发现值得进入的内容 | 代表摄影、克制介绍、清楚的栏目入口、少量真实精选 |
| 生活与摄影 | 看照片、了解一个具体片刻 | 按事件分组，保留照片比例、说明与时间 |
| 学习与思考 | 找文章、连续阅读、分享链接 | 可扫描的列表、独立详情页、清晰的正文排版 |
| 国旗护卫队 | 了解事件先后与共同经历 | 时间线概览；素材足够时再扩展事件详情 |

三个栏目共享字体、间距、色彩和导航规则，各自采用适合内容的结构。首页精选只取明确选定的公开真实内容；数量不足时缩减区域，不用演示记录填满页面。

## 3. 第一轮：首页与整体视觉

### 比较三个方向

| 方向 | 收益 | 取舍 |
| --- | --- | --- |
| A：延续沉浸摄影封面 | 接近当前气质，改动集中，照片有感染力 | 内容发现仍依赖栏目入口，移动裁切需仔细处理 |
| B：浅色编辑式首页 | 最新文章与记录更容易扫描 | 对真实内容储备要求较高，摄影的第一印象减弱 |
| C：摄影封面加内容精选（建议） | 保留摄影辨识度，也能让访客发现具体记录 | 首页更长，需要控制图片体积和内容密度 |

建议先以 C 为重点比较对象，A 与 B 作为参照。具体色彩、照片比例和模块位置以视觉稿比较后确定。

### 第一轮工作顺序

1. 启动现有本地站点，获取当前首页桌面与手机截图，记录视口和状态。
2. 查看原图，确认自行车、人物、文字或水印等主体的保留要求；核对可公开内容。
3. 使用相同真实文案与照片制作三个方向的首页视觉稿，比较信息层级和气质。
4. 用户选择主要方向，并指出希望保留和调整的部分。
5. 提炼一份视觉规范：中文字号、正文行高、字体回退、色彩变量、页面宽度、间距、图片比例、焦点与悬停状态、少量过渡效果。
6. 在原有 Astro 页面和组件中实现首页，随后核对内页外壳的一致性。
7. 提供可运行预览、同视口截图、改动说明和实际检查结果。

首轮验收重点：能快速理解“这是谁、这里有什么、从哪里进入”；手机首屏文字清楚、入口容易点击；照片主体与文案不互相遮挡；页面下方有内容时能看出可继续浏览。

## 4. 工具职责与选择规则

工具清单根据本会话暴露的技能与工具编排，不等于已经逐一验证本机所有扩展可运行。

| 工具或 skill | 适用阶段 | 在本项目的职责 |
| --- | --- | --- |
| brainstorming | 每一轮开始 | 明确目标、取舍、范围与验收，先解决会影响整页的选择 |
| Product Design ideate | 首页视觉探索 | 基于当前截图和真实素材制作候选视觉稿；选择后再落地 |
| imagegen | 需要视觉稿或确有资产缺口时 | 生成设计比较稿；纪实照片继续使用真实原图 |
| ui-ux-pro-max | 设计决策与检查 | 提供排版、布局、交互及可访问性参考；由项目内容与现有规则筛选建议 |
| design-system | 方向确定后需要系统化时 | 整理有限且可复用的变量与组件规则，不重复建立多个规范源 |
| ui-styling | 具体组件需要时 | 参考交互状态与样式方法，按 Astro/CSS 实现；引入新框架须有具体收益 |
| Product Design image-to-code | 已选视觉稿落地时 | 忠实实现选定布局，并与同视口截图对照 |
| 浏览器工具 | 基线、交互检查、验收 | 使用当前可用且适合的浏览器；核验实际导航、布局和状态 |
| Product Design audit | 成型后体验审查 | 先截图取证，再指出有位置、有影响的体验问题 |
| verification-before-completion | 每轮交付前 | 根据实际执行结果区分完成、未验证和待处理 |
| html-render-check | 单文件页面或报告确实需要时 | 补充运行与渲染检查；Astro 正常页面优先沿用现有验收脚本 |
| Sites | 明确选择其托管时 | 可作为独立预览或托管选项；本项目继续沿用已有本地工程与发布路线 |

本轮实际执行过一次 ui-ux-pro-max 设计检索。返回的编辑式网格和层级原则可供参考；滚动叙事、粉色强调和远程英文字体未被采纳。它们与当前内容、中文阅读和既有视觉约定不够贴合。

每个阶段只保留一份当前认可的设计规范；后续工具都以它为依据，避免重新生成一套互相冲突的风格。

## 5. 后续构建顺序

| 轮次 | 范围 | 交付与完成条件 |
| --- | --- | --- |
| 第一轮 | 首页与整体视觉 | 选定方向、视觉规范、可运行首页、桌面及手机核对 |
| 第二轮 | 生活与摄影 | 用已有真实记录检验多图、横竖图、长说明和日期；需要时增加看大图能力 |
| 第三轮 | 笔记与文章 | 列表进入独立详情页；支持标题、正文、代码、引用、图片与分享地址；文章较长时再加目录 |
| 第四轮 | 国旗护卫队 | 用真实事件检验时间线、照片与说明；整理好内容后替换演示记录 |
| 第五轮 | 内容发现与发布准备 | 内容量需要时增加标签、归档、搜索；核验元信息、索引策略、站点地图及 RSS 需求 |

每轮只对本轮关键体验作决定。用户主要判断照片、气质、内容顺序和阅读感受；开发侧负责组件、响应式、浏览器核验与问题修复。反馈尽量落到具体位置，例如“手机封面的自行车被裁掉”“文章标题与日期分不清层级”。

## 6. 开发与验收循环

统一循环：明确目标 → 读取相关文件与 Git 基线 → 设计或确认局部方案 → 实现 → 顺序运行检查与构建 → 浏览器验收 → 修复 → 交付。

沿用 `scripts/local.ps1` 选择项目运行时。类型检查与构建按顺序执行，避免历史上出现过的 Windows 缓存竞争。按变更选择现有脚本：

- 页面与组件：`check`、相关 `test`、`build`、`test:output`、`test:framework`。
- 素材入口：增加 `test:materials`；修改开发时自动发现行为时再执行 `test:materials:dev`。
- 页面、路由和运行边界：执行相关开发/生产 HTTP 与浏览器验收，保留旧链接、SSR/API 和敏感路径边界。
- 安全边界相关变更与发布前：执行 `check:security`。纯样式修改无需机械启动整套数据库测试。

浏览器核验覆盖 320/375px 小屏、768px 平板、1440px 桌面，并在布局断点附近抽查。验证点击、键盘焦点、图片加载、无横向溢出、长标题、空内容、减少动画偏好；关键导航在无 JavaScript 时仍可使用。

完成不以“服务已启动”或“HTTP 200”为依据：应有可浏览结果、真实交互验证与截图核对。每轮记录已开发、已验证、已部署、已提交/推送四种状态。发布沿用本地完成、用户验收、授权上线的顺序，并核验线上内容与回滚材料。

## 7. 优化顺序与问题分类

### 优先级

1. P0：链接错误、内容缺失、图片错误、草稿暴露、手机无法操作等阻断问题。
2. P1：导航与阅读层级、手机布局、照片裁切、文字对比度、键盘操作。
3. P2：图片尺寸与加载、字体、脚本成本、布局稳定、元信息与索引。
4. P3：细微过渡、装饰效果和非必要功能。

视觉与功能验收后先测量，再优化。性能目标参考 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1；线上评价按移动端和桌面端的真实访问第 75 百分位判断。本地 Lighthouse 或模拟网络结果单独记录，不能直接代替线上真实用户数据。

文字对比度以 WCAG AA 普通文字至少 4.5:1、大号文字至少 3:1 为基础；封面文字需要针对实际照片背景检查。触控区域建议按约 44 CSS px 设计，作为项目易用性目标，不混同于所有 WCAG 条款的最低尺寸。

### 遇到问题先分类

| 分类 | 示例 | 处理方式 |
| --- | --- | --- |
| 架构设计问题 | 所有正文塞进列表，缺乏独立可分享地址 | 调整页面与内容边界，再整理组件 |
| 参数或阈值问题 | 手机封面高度不合适、文字太淡、图片输出过大 | 在实际屏幕和测量结果基础上调整变量 |
| 运行异常 | 图片路径错误、内容解析失败、路由 404 | 定位输入、日志和具体代码，修复后回归 |

先判断是否存在影响多个模块的共同根因。例如三页字号同时不合理，应检查共享排版规则；不要逐页叠加覆盖。
