## 1. 先纠正一个常见误解

### 「纯 HTML/CSS 性能好」这句话只对了一半

需要区分两件事：

| | 含义 | 谁决定 |
|---|---|---|
| **交付性能** | 文件传到浏览器后渲染多快 | 文件体积、请求数、渲染方式 |
| **实现方式** | 这些文件是怎么产生和维护的 | 构建工具、模板、数据来源 |

纯 HTML/CSS 的**交付性能确实是天花板**——没有 JS 执行、没有请求瀑布、首屏即渲染。

但当前 README 里规划的方案是：

```
index.html（空壳）→ main.js → fetch data/posts.json → JS 渲染出内容
```

**这不是纯 HTML/CSS，而是客户端渲染（CSR）。** 它同时丢掉了两样东西：

- ❌ 丢掉纯静态的速度（内容要等 JS 跑完才出现）
- ❌ 也没有框架的维护性（还是要手写 HTML 骨架和渲染逻辑）

这是最差的一种组合。

### 三种方式的真实差距

以下为**估算值**（4G 网络、中端手机、页面含 10 条列表 + 5 张图），非实测：

| 方案 | 请求链 | LCP 估算 | CLS | SEO |
|---|---|---|---|---|
| 纯静态 HTML（内容直写） | HTML → CSS | ~0.8s | 0 | ✅ |
| JSON + JS 客户端渲染（当前规划） | HTML → JS → JSON → 渲染 → 图 | ~2.5s | ⚠️ 有跳动 | ❌ 空壳 |
| **SSG 预渲染**（Astro/Hugo） | HTML → CSS | **~0.8s** | 0 | ✅ |

> ⚠️ 数字是量级估算，用于说明差距，不是基准测试结果。

## 2. 关键认知：构建发生在本地，不在服务器

这是整个选型的转折点。

项目有一条硬约束：

> 服务器只放运行所需的项目代码，不放 Node 运行时。

很多人因此认为「不能用框架」。**这是错的。**

```
本地（有 Node）                    服务器（无 Node）
─────────────────                 ─────────────────
Markdown 源文件                    dist/ 纯静态产物
    ↓ astro build          →       ├── index.html
生成静态 HTML/CSS/JS               ├── posts/xxx/index.html
                                   └── _astro/*.css
```

**构建步骤完全在本地完成，服务器收到的仍然是纯静态文件。**

所以「服务器只放静态文件」这条约束，**不构成对 SSG 的任何限制**。真正被限制的只有「服务器端运行时」（SSR、Node 服务、数据库），而博客本来就不需要。

## 3. 你的四类内容，需要什么能力

| 内容 | 更新频率 | 特征 | 架构需求 |
|---|---|---|---|
| 日常（朋友圈式） | 高 | 短文本 + 多图 + 时间流 | 图片优化、瀑布流、懒加载、无限滚动 |
| 文章 | 中 | 长文、需沉浸阅读 | Markdown、目录、代码高亮、阅读进度 |
| 学习笔记 | 中 | 结构化、会互链、需检索 | 分类树、标签、全文搜索、双链 |
| 大事记 | 低 | 策展式、时间轴、有图有故事 | 时间轴组件、数据驱动渲染 |

**四类内容模型完全不同。** 用一套手写 HTML 同时承载它们，会迅速失控：

- 每加一篇日常要手写一段 HTML
- 笔记之间无法自动生成索引和反向链接
- 搜索、标签、归档全部要自己写
- 改一次样式要动几十个文件

内容量一旦超过 ~30 条，手写 HTML 的维护成本会超过学习框架的成本。

## 4. 候选方案对比

| 维度 | 纯静态手写 | **Astro（推荐）** | Hugo | Eleventy | React/Vue SPA |
|---|---|---|---|---|---|
| 交付性能 | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★☆ |
| 默认 JS 体积 | 0 | **0**（islands 按需） | 0 | 0 | 大 |
| 写作体验 | 手写 HTML | Markdown/MDX | Markdown | Markdown | 任意 |
| 图片优化 | 手动 | **内置**（sharp → WebP/AVIF + srcset） | 需配置 | 需插件 | 需配置 |
| 组件化 | 无 | ✅ | 弱（partials） | 弱 | ✅ |
| 交互组件 | 手写 JS | ✅ islands | 手写 JS | 手写 JS | ✅ |
| 学习曲线 | 最低 | 中 | 中高（Go 模板） | 中 | 高 |
| 构建速度 | — | 快 | **最快** | 快 | 中 |
| 服务器要求 | 纯静态 | **纯静态** | 纯静态 | 纯静态 | 纯静态 |
| 适合你 | 内容量小 | ✅ **四类内容** | 纯博客 | 高度定制 | ❌ 内容站 |

### 为什么推荐 Astro

1. **默认零 JS**：不写交互组件时，输出就是纯 HTML/CSS，交付性能和手写 HTML 完全一样。
2. **Islands 架构**：只有真正需要交互的部分（图片灯箱、搜索框）才加载 JS，且互不干扰。
3. **Content Collections**：四类内容各定义一套 schema，写作时字段填错会在构建时直接报错。
4. **内置图片优化**：自动生成多尺寸 + 现代格式，这是你这种图片密集型站点最大的性能杠杆。
5. **输出纯静态**：`dist/` 直接同步到 `/srv/nuwanda-blog/web/`，现有部署流程不用改。

### 为什么不选其他

- **Hugo**：构建最快，但 Go 模板语法陡峭，组件化弱，图片处理不如 Astro。如果你只想写纯文字博客，它是好选择；但你有图片流和交互需求。
- **Eleventy**：灵活，但「灵活」意味着大量东西要自己拼装，对学习阶段不友好。
- **React/Vue SPA**：内容型站点用 SPA 是负优化——首屏要等 JS，SEO 差。除非你要做重交互应用，否则不适用。

## 5. 性能预算（具体目标）

架构定了之后，用数字约束实现：

| 指标 | 目标 | 说明 |
|---|---|---|
| HTML（gzip） | < 15 KB | 每页 |
| CSS（gzip） | < 20 KB | 全站共用一份 |
| JS（gzip） | < 10 KB | 仅含交互的页面 |
| 字体请求 | **0** | 用系统字体栈 |
| LCP（4G 中端机） | < 1.2 s | |
| CLS | < 0.02 | 图片必须预留宽高 |
| 图片单张 | < 150 KB | 列表缩略图 |

### 关于中文字体（重要）

一个完整的中文字体文件是 **3–10 MB**，直接引入会毁掉所有性能优化。

**建议：用系统字体栈，不引入 Web 字体。**

```css
font-family: -apple-system, BlinkMacSystemFont, "Segoe UI",
             "PingFang SC", "Hiragino Sans GB",
             "Microsoft YaHei", "Source Han Sans SC",
             sans-serif;
```

这样零请求、零延迟，且在 Mac/Windows/手机上都能拿到高质量中文字形。

如果将来一定要用自定义字体（比如标题用宋体），必须：

1. 只对**标题**用，正文保持系统字体
2. 用 `fonttools` 做**子集化**，只保留用到的字
3. `font-display: swap` + `<link rel="preload">`

## 6. 站点信息架构

```
/                        首页 —— 混合信息流（最新日常 + 精选文章）
│
├── /moments/            日常 —— 朋友圈式照片流
│   └── /moments/<id>/   单条详情（可选）
│
├── /posts/              文章列表
│   └── /posts/<slug>/   文章详情
│
├── /notes/              学习笔记索引
│   └── /notes/<slug>/   笔记详情
│
├── /timeline/           国旗护卫队大事记
│
├── /about/              关于
├── /tags/<tag>/         标签聚合
└── /search/             全站搜索
```

### 为什么首页做「混合流」

四类内容分四个入口会让首页变得空洞。混合流能体现「这是一个活着的个人站」：

```
[日常] 今天去了……                   3 张图
[文章] 关于 XX 的思考                 封面
[日常] 随手记……                     1 张图
[笔记] 数据库索引学习笔记
[大事记] 2026 年国庆升旗
```

## 7. 内容数据模型

```ts
// 日常
{ date, text, images[], location?, mood?, tags[] }

// 文章
{ title, date, tags[], summary, cover?, draft?, updated? }

// 笔记
{ title, date, category, tags[], order?, summary? }

// 大事记
{ date, title, description, images[], importance?, location? }
```

统一约定：

- 日期一律 `YYYY-MM-DD`
- `slug` 小写 + 短横线，与 OSS 路径 `images/posts/<slug>/` 对齐
- 图片字段**只存相对 key**，不存完整 URL（见 [storage.md](../storage.md) 第 5 节）

## 8. 图片策略（性能的最大杠杆）

对图片密集型站点，**图片策略对性能的影响远大于框架选择**。一张 5 MB 的原图能毁掉任何架构的优势。

| 环节 | 做法 |
|---|---|
| 上传 | 本地转 WebP/AVIF，原图归档到 OSS 低频存储 |
| 尺寸 | 生成 3 档：480 / 960 / 1600 px |
| 引用 | `srcset` + `sizes` + `loading="lazy"` + `decoding="async"` |
| 布局 | 必须写 `width`/`height` 或 `aspect-ratio`，防 CLS |
| 首屏 | 首图用 `loading="eager"` + `fetchpriority="high"` |
| 缓存 | OSS 设 `Cache-Control: public,max-age=31536000,immutable` |
| 防护 | 防盗链 Referer 白名单（见 storage.md 第 7 节） |

## 9. 视觉方向：如何做出「简洁、高级」

「高级感」在网页上几乎等同于**克制**：

| 要素 | 做法 | 反例 |
|---|---|---|
| 排版 | 行宽 65–72 字符，字号阶梯 1.25 倍，行高 1.7 | 满屏宽文字 |
| 留白 | 宁可多，不可少 | 元素挤在一起 |
| 配色 | 1 个强调色 + 中性灰阶（8 个变量足够） | 五颜六色 |
| 字体 | 系统字体栈，最多 2 个字重 | 4 种字体混用 |
| 边框 | 用 1px 细线或极浅阴影 | 重投影、渐变 |
| 动效 | 150–250ms，只用于状态反馈 | 花哨入场动画 |
| 暗色模式 | 用 CSS 变量一键切换 | 硬编码颜色 |

**参考对象**（均为 MIT，可安全借鉴，详见 [research/open-source-designs.md](../research/open-source-designs.md)）：

- **poole** — 排版基线（行宽、字号阶梯、留白），最适合当 CSS 起点
- **hugo-PaperMod** — 信息架构（首页列表 / 归档 / 标签 / 搜索）
- **mzlogin** — 中文排版细节

## 10. 建议的实施路径

不要一次做完。按内容价值排序，每阶段都能上线：

| 阶段 | 内容 | 产出 |
|---|---|---|
| **A** | Astro 骨架 + 设计系统（CSS 变量、排版、暗色模式） | 首页 + 关于页 |
| **B** | 文章模块 | 列表 + 详情 + 标签 |
| **C** | 笔记模块 | 索引 + 详情 + 搜索 |
| **D** | 日常模块 | 照片流 + 灯箱 |
| **E** | 大事记 | 时间轴 |
| **F** | 打磨 | 性能预算达标、SEO、RSS |

每阶段结束后跑一次性能预算检查，避免后期返工。

## 11. 决策建议

### 推荐方案

> **Astro（SSG + Islands），本地构建，产物同步到现有 Nginx。**

理由：

1. 交付性能与手写 HTML 持平（默认零 JS）
2. 四类内容各有 schema，长期可维护
3. 内置图片优化，直接解决你最大的性能瓶颈
4. 产物是纯静态文件，**现有服务器架构和部署流程完全不用改**
5. 学习成本一次性投入，换来后续所有内容的写作效率

### 如果你不想引入构建工具

那就**必须放弃「JSON + JS 渲染」这条路**，改为：

- 内容直接写进 HTML（纯静态）
- 用 Python 脚本在本地把 Markdown 生成 HTML（相当于自己写一个极简 SSG）

这样性能一样好，但你要自己维护生成脚本。**本质上还是在做 SSG，只是更费劲。**

### 需要你确认的问题

1. 是否接受「本地需要安装 Node.js 并执行构建」？
2. 四类内容里，哪一类最先做？（建议从「文章」或「日常」开始）
3. 是否要中文全文搜索？（影响是否引入 Pagefind 之类的工具）
